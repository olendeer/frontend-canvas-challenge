# Канвас генераций — решение тестового задания

Редактор цепочек «текст → генератор → результат» на React Flow: пространства, ноды, связи,
автосохранение графа через REST и тестовая генерация изображения.
Next.js 16 (App Router) + TypeScript, клиентский рендер, серверное состояние — TanStack Query.

Условия: [задание](../../docs/ASSIGNMENT.md) · [интеграция](../../docs/INTEGRATION.md) ·
[критерии](../../docs/EVALUATION.md).

## Запуск

Из корня репозитория, после `npm ci`:

```sh
npm run dev        # бэкенд на http://localhost:4001
npm run dev:web    # фронтенд на http://localhost:3000
```

Команды нужно держать в двух терминалах: `dev` поднимает API, `dev:web` — фронтенд.
Адрес API берётся из `NEXT_PUBLIC_API_URL`, по умолчанию `http://localhost:4001`. Если API
запущен на другом порту, скопируйте `apps/web/.env.example` в `apps/web/.env.local` и
поправьте значение.

Сборка и запуск собранного фронтенда:

```sh
npm run build:web
npm run start:web
```

Проверки:

```sh
npm run typecheck:web   # tsc --noEmit
npm run test:web        # юнит-тесты правил и очереди записи (vitest)
npm run e2e:web         # сквозные сценарии в браузере (playwright)
```

Для `e2e:web` один раз нужен `npx playwright install chromium`. Playwright сам поднимет API и
фронтенд, если они ещё не запущены. Зависимости зафиксированы в корневом
`package-lock.json`. Проверялось на Node 20.20 и npm 11.14; ограничение `engines` в корневом
`package.json` я не менял.

## Как устроено решение

Слои лежат в `src/`, зависимости направлены внутрь: `core → data → domain → features`.

```
core/      инфраструктура, ничего не знает про канвас
  http/            HttpClient (интерфейс), HttpError, Endpoint
  adapters/fetch/  ЕДИНСТВЕННОЕ место с fetch во всём приложении
  sync/            WriteQueue: debounce + строгая очередь записи одного ресурса
  store/           ObservableStore под useSyncExternalStore
  idempotency/     журнал ключей идемпотентности в localStorage
  storage/         интерфейс хранилища + адаптер localStorage
data/      доступ к API
  endpoints.ts     ЕДИНСТВЕННОЕ место, где живут адреса
  repositories/    по репозиторию на область, метод = вызов API
  dto/             разбор конверта ошибки, абсолютный адрес картинки
domain/    правила и сервисы без React
  graph/           правила графа (индекс, связи, тело PUT) и сервис версий (ETag)
  generation/      индекс генераций, пауза опроса, запуск с ключом идемпотентности
  errors/          коды API → тексты с подсказкой, что делать
  config/          значения GET /api/config и их значения по умолчанию
features/  экраны: *.module.tsx + *.hooks.ts
  canvas/          черновик графа, контроллер записи, ноды, тулбар, статус сохранения
  spaces/          создание и список пространств
  error-alert/     единственный способ показать ошибку запроса с кнопкой повтора
query/     кэш серверного состояния: <область>/*.queries.ts, ключи и клиент
ui-kit/    Button, Field, TextArea, Select, Alert, StatusBadge, Card, …
```

Компонент — это папка со своим `index.ts`. Переиспользуемые компоненты в `ui-kit` называются
`<имя>.component.tsx`, экраны и их части в `features` — `<имя>.module.tsx`, поэтому по имени
файла видно, знает ли компонент про данные.

Поток данных: `страница → модуль фичи → *.hooks.ts (TanStack Query) → useXxxService() →
доменный сервис → репозиторий → HttpClient`. Компонент никогда не обращается к сети напрямую
и никогда не разбирает ответ: он получает данные с типами или готовый текст ошибки через
`getErrorMessage(error)`.

## Работа с API

Все запросы идут через `FetchAdapter` — единственное место в приложении, где вызывается
`fetch`. Он собирает заголовки (`Accept`, `Content-Type`, `If-Match`, `Idempotency-Key`),
сериализует тело, проверяет статус, разбирает JSON с учётом ответов без тела (204 и 304) и
вытаскивает `ETag`, `Location`, `Retry-After` и `X-Request-Id`. Наружу выходит либо
`HttpResponse<TData>` с типизированными данными, либо `HttpError` — сетевая ошибка, HTTP-ошибка
и ошибка разбора приведены к одному виду в одном месте. Ни один компонент не видит `Response`,
не вызывает `response.ok` и не пишет свой `catch`.

Адреса живут в `data/endpoints.ts`, разбор конверта `{"error":{"code","message"}}` — в
`ApiErrorDto`, перевод кода в текст с подсказкой — в `domain/errors/error-message.ts`.
Добавить запрос — это строка в `endpoints.ts`, метод репозитория и хук в `query/`.

**Версия графа.** `GraphServiceImpl` держит `Map<spaceId, ETag>`: `read` кладёт туда ETag из
заголовка ответа, `save` сам подставляет его в `If-Match` и записывает новый ETag из ответа
PUT. Запуск генерации берёт ту же версию через `getVersion` и передаёт её в теле как
`graphETag`. ETag нигде не передаётся через пропсы и не вычисляется на клиенте. Если версии
почему-то нет, `save` сначала читает граф — так `428 PRECONDITION_REQUIRED` не может
случиться.

**Ключи идемпотентности.** `IdempotencyJournal` хранит в `localStorage` пару «намерение →
ключ + отпечаток тела». Повтор запуска с тем же телом получает прежний ключ, поэтому потерянный
ответ не создаёт вторую генерацию даже после перезагрузки страницы. Как только сервер принял
запуск, ключ освобождается — следующий запуск той же ноды получит новый ключ, и тестовый отказ
можно повторить.

## Debounce и очередь сохранений

`WriteQueue` в `core/sync` ничего не знает про граф: ему передают `getDelayMs`, функцию
чтения тела и функцию записи. Логика такая:

1. Любая правка черновика вызывает `schedule()`: ставится признак «есть несохранённые правки»
   и перезапускается таймер на `debounceMs` из `GET /api/config` (500 мс). Серия быстрых правок
   даёт один PUT после паузы.
2. Таймер отправляет запись. Тело читается **в момент отправки** (`read()`), поэтому уходит
   всегда самое свежее состояние, а не то, что было при постановке в очередь.
3. Пока запрос в полёте, новые правки только помечаются: параллельного PUT того же графа не
   бывает. После ответа очередь отправляет актуальное состояние — либо сразу, если таймер уже
   отработал, либо по следующему срабатыванию таймера, чтобы непрерывный ввод не превращался в
   поток запросов.
4. Ответ сервера **не пишется обратно в черновик**: из него берётся только новый ETag. Поэтому
   ответ старого запроса физически не может затереть более свежие правки.
5. `flush()` снимает таймер, отправляет отложенное сразу, дожидается всей цепочки и бросает
   ошибку записи. Кнопка генерации вызывает его первым делом, поэтому учитывает и ещё не
   сработавший debounce, и уже отправленный запрос. Ошибка сохранения прерывает запуск.
6. Ошибка записи не приводит к автоповтору — иначе при недоступной сети получился бы цикл.
   Повтор происходит при следующей правке или по кнопке «Повторить сохранение».
7. `412 GRAPH_VERSION_CONFLICT` объявлен блокирующей ошибкой (`getIsGraphConflict`): очередь
   встаёт, черновик остаётся как есть, интерфейс показывает конфликт и кнопку «Перечитать
   граф». Она читает серверный граф, заменяет им черновик и снимает блокировку. Слияния версий
   нет — это и не требовалось.

Состояние очереди — это внешнее хранилище (`ObservableStore` + `useSyncExternalStore`), и
`SaveStatus` — единственное место, где оно превращается в подпись: «Сохранено», «Есть
несохранённые правки», «Сохраняем…», «Не сохранено», «Конфликт версий».

**Опрос генерации.** Опрашивается один запрос — список генераций пространства, с
`refetchInterval` из доменного правила `getPollDelayMs`. Пока в списке есть `processing`,
пауза берётся из `Retry-After` ответа 202, иначе из `pollIntervalMs` настроек; когда активных
попыток нет, правило возвращает `false` и опрос останавливается сам. Уход со страницы или
закрытие пространства снимает подписку в TanStack Query. Отдельного цикла опроса на ноду нет:
состояние всех нод берётся из одного индекса по этому списку — это же и восстановление после
перезагрузки. Я осознанно не опрашиваю каждую генерацию по её `Location`: тогда пришлось бы
держать два источника статуса и сливать их, а выигрыш нулевой — активных попыток единицы.

## Обработка данных: разбор одного участка

**Участок: проверка связи при перетаскивании.** React Flow вызывает `isValidConnection` на
каждом кадре, пока пользователь тянет связь, и для каждого порта под курсором — это десятки
вызовов в секунду. Проверить нужно четыре условия: типы обеих нод совместимы, вход цели не
занят, у генератора ещё нет результата, это не петля.

Прямая реализация на массивах — это `nodes.find` дважды и `edges.some` дважды, то есть четыре
линейных прохода на каждый вызов: `O(нод + связей)` × кадры, и всё это внутри жеста, где кадр
и так занят перерисовкой канваса.

В решении `buildGraphIndex` собирает индекс за **два прохода** — один по нодам, один по
связям, без промежуточных массивов:

- `kindById` — тип каждой ноды;
- `promptTextById` — текст текстовых нод;
- `sourceByTarget` — источник занятого входа;
- `resultByGenerator` — результат, занятый генератором.

После этого `getIsValidConnection` — это четыре обращения к `Map` и ноль аллокаций на вызов.
Тем же индексом пользуется `getChainIssue`: он повторяет серверную проверку `INCOMPLETE_CHAIN`
и отвечает, чего не хватает генератору для запуска, тоже за `O(1)`.

**Частота пересборки индекса.** Индекс живёт в снимке черновика и пересобирается только тогда,
когда изменилась структура или данные нод: добавление, удаление, связь, правка текста.
Перетаскивание ноды — это изменения типа `position`, выделение — `select`, замер размеров —
`dimensions`; ни одно из них индекс не трогает, и прежняя ссылка переезжает в новый снимок как
есть. Поэтому перетаскивание 20 нод при 60 кадрах в секунду не делает ни одного лишнего
прохода, а `useCallback` для `isValidConnection` не пересоздаётся. Изменения разбираются одним
проходом по массиву `changes` (в нём обычно один элемент), который заодно собирает `Set`
удалённых нод — и только если удаление действительно было.

**Выделение памяти.** Индекс — это четыре `Map` с примитивными значениями. Он не держит ссылок
на объекты нод: во-первых, не удерживает удалённые ноды от сборки мусора, во-вторых, не может
разойтись с координатами, которые в нём и не нужны.

**Соседние участки, где это же правило применено.**

- `toGraphPayload` (тело PUT, вызывается один раз на сохранение) — один `map` по нодам и один
  по связям. Именно `map`, а не `new Array(n)` с записью по индексу: `new Array(n)` создаёт
  массив с дырками (`HOLEY_ELEMENTS` в V8), и последующее заполнение его таким и оставляет, а
  `map` по плотному массиву даёт плотный результат. `reduce` с `push` сделал бы столько же
  проходов и читался бы хуже. Объекты `data` и `position` переиспользуются по ссылке — они
  никогда не меняются на месте, поэтому копия не нужна, и на сохранение выделяется по одному
  объекту-обёртке на ноду и на связь.
- `dropEdgesTouching` (удаление ноды вместе со связями) — один проход, который выделяет массив
  только если что-то действительно удаляется, а иначе возвращает прежнюю ссылку; тогда React
  Flow не перерисовывает связи вовсе. Промежуточного массива из `filter` перед проверкой нет.
- `withNodeData` (правка текста на каждое нажатие клавиши) — один `map`, в котором новый объект
  создаётся только для изменённой ноды; остальные сохраняют ссылки, и React Flow
  перерисовывает одну ноду, а не все.
- `buildGenerationIndex` — один проход по списку генераций, который приходит от новых к старым,
  поэтому первое попадание и есть самая свежая попытка: `byNode` для генераторов, `byResultNode`
  для нод результата. Без индекса каждая нода искала бы свою попытку через `find`, то есть
  `O(ноды × генерации)` на каждую перерисовку. Строить полный список попыток каждой ноды,
  когда нужна только первая, смысла нет.
- `getPollDelayMs` использует `some`, а не подсчёт: активная попытка стоит в начале списка,
  поэтому проверка обрывается на первом элементе.

Про `.map().filter()` и `.reduce()`. Цепочка `map().filter()` делает два прохода и создаёт
промежуточный массив, который сразу выбрасывается, — там, где нужно и отфильтровать, и
преобразовать, это один проход (`dropEdgesTouching`). Но `reduce` сам по себе преимущества не
даёт: одиночный `map` — это уже один проход, и заменять его на `reduce` только ради названия
метода я не стал. Отдельно про накопитель: `reduce`, который на каждом шаге делает `{...acc}`
или `[...acc, x]`, копирует растущий результат и превращает линейную задачу в квадратичную,
поэтому индексы наполняются `Map.set` на одном экземпляре. Дырок в массивах не появляется:
элементы не удаляются через `delete`, а массивы пересобираются через `filter`, `slice` и `push`.

Отдельно про повторные запросы: правка одной ноды не перечитывает граф и не пересчитывает
серверное состояние. Черновик — единственный источник правды для редактирования, серверный граф
читается один раз при открытии пространства и по явной кнопке после конфликта.

## Проверенные сценарии

Автоматически, `npm run e2e:web` — 15 сценариев в браузере, все проходят:

1. Пространство создаётся через API и открывается по адресу `/spaces/{id}`; добавляются три
   типа нод с уникальными идентификаторами, правка текста видна сразу, граф уходит на сервер.
2. Связи создаются перетаскиванием между портами; «текст → результат» и второй вход генератора
   отклоняются; удаление ноды кнопкой убирает её связи, и сервер принимает оставшийся граф.
3. Серия быстрых правок даёт ровно один PUT, одиночная правка тоже сохраняется.
4. При медленном ответе (искусственная задержка 1200 мс) PUT одного графа не накладываются, а
   правка, сделанная во время запроса, доезжает до сервера последней.
5. Конфликт версий: сторонний PUT меняет граф, следующая правка получает 412, черновик остаётся
   на канвасе, генерация не запускается, кнопка «Перечитать граф» возвращает серверную версию.
6. Генерация сразу после правки: сервер получает свежий текст, потому что запуск дождался
   сохранения.
7. Перезагрузка страницы восстанавливает граф, связи и результат; перезагрузка во время
   генерации доводит её до изображения.
8. Тестовый отказ показывает ошибку и допускает повтор: повтор с тем же телом создаёт новую
   генерацию (ключ освобождён), переключение на «Успех» — третью, с картинкой.
9. Двойное нажатие кнопки генерации не создаёт вторую генерацию.
10. Потерянный ответ на запуск: запрос дошёл до сервера, ответ оборван — повтор с прежним
    ключом не создаёт дубль, генераций по-прежнему одна.
11. Опрос прекращается после завершения: за 2,5 секунды после результата ни одного запроса.
12. Результат не подставляется в чужую ноду: после удаления ноды результата и подключения новой
    в ней пусто, старая картинка не переезжает.
13. Положение канваса сохраняется и восстанавливается после перезагрузки.
14. Удаление ноды клавишей Delete убирает её связи, сервер принимает граф.
15. Пространство создаётся с клавиатуры, кнопка добавления ноды срабатывает по Enter, при
    ширине 1280 горизонтальной прокрутки нет.

Юнит-тесты, `npm run test:web` — 31 проверка: поведение `WriteQueue` (один PUT после серии
правок, отсутствие параллельных записей, отправка последнего состояния, `flush`, отсутствие
автоповтора, блокировка после конфликта, стабильность снимка), правила графа (индекс,
допустимые и запрещённые связи, занятые порты, готовность цепочки, тело PUT с отсечением
служебных полей и ограничением координат, сохранение ссылок, раскладка новых нод), правила
генераций (свежая попытка на ноду и на результат, счётчик активных, пауза опроса), разбор
ошибки API и журнал идемпотентности.

Вручную: проверил `npm run build:web` и `npm run start:web` на собранной сборке, а также
`npm run smoke` при работающем API.

## Осознанные решения

- **Постоянные данные отделены от служебных полей React Flow.** Тип ноды канваса — это
  `Node<данные из схемы API, тип>`, а тело PUT собирается функцией `toGraphPayload`, которая
  берёт только `id`, `type`, `position`, `data`. `selected`, `dragging`, `measured` и размеры
  на сервер не уезжают, а функции-обработчики в `data` не попадают вообще: ноды получают
  действия из контекста, поэтому в графе нет ничего несериализуемого.
- **Черновик графа — внешнее хранилище, а не `useState`.** Очереди записи нужно прочитать
  актуальное состояние в момент отправки, а нодам — вызвать действие, не перерисовывая канвас.
  `ObservableStore` + `useSyncExternalStore` решают и то, и другое, и заодно позволяют тестировать
  весь черновик без React.
- **Два контекста вместо одного.** Стабильные действия (`CanvasActionsContext`) отделены от
  состояния (`CanvasStatusContext`), поэтому перетаскивание нод не меняет ни один контекст и не
  перерисовывает ноды, а изменение статуса генерации не пересоздаёт обработчики.
- **Сохранение графа — не мутация TanStack Query.** Мутации не умеют ни debounce, ни строгой
  очередности, ни «отправить самое свежее состояние вместо того, что было при постановке».
  Поэтому запись графа живёт в `core/sync`, а `query/` остаётся слоем кэша серверного
  состояния: список пространств, пространство, граф при открытии, генерации с опросом.
- **Прослойки без поведения не заведены.** Для графа и генераций есть доменные сервисы, потому
  что там живут версии и ключи идемпотентности. Для настроек и пространств наружу выходит сам
  репозиторий: сервис, который просто пересылает вызов, ничего бы не дал.
- **Результаты не хранятся в графе.** Схема графа их не принимает, поэтому изображение и статус
  берутся из списка генераций по `resultNodeId` — самая свежая попытка для существующей ноды.
  Это же автоматически закрывает требование не подставлять результат в чужую или удалённую
  ноду: сопоставление идёт по сохранённому в генерации идентификатору, а не по текущим связям.
- **Клиентские правила повторяют серверные, а не заменяют их.** `getIsValidConnection` и
  `getChainIssue` описаны один раз и совпадают с проверками `INVALID_GRAPH` и
  `INCOMPLETE_CHAIN`: интерфейс не создаёт связь, которую сервер отвергнет, но решение о
  корректности всё равно остаётся за сервером — успех рисуется только по его ответу.
- **Координаты ограничиваются при сохранении.** Схема API допускает ±10000, поэтому
  `toGraphPayload` подрезает и округляет позиции: иначе далеко утащенная нода ломала бы
  сохранение ответом 400 с невнятной причиной. Округление заодно уменьшает число PUT с
  одинаковым содержимым.
- **Макета нет**, интерфейс собран на SCSS-модулях без UI-библиотеки. Значения темы — CSS-
  переменные в `app/globals.scss`, повторяющиеся блоки (`stack`, `row`, `focus-ring`,
  `card-surface`, `loading-state`) — миксины в `styles/`.
- **Новые ноды раскладываются по колонкам** «текст — генератор — результат»: цепочка сразу
  выглядит как цепочка, а порты оказываются напротив друг друга.

## Известные недоработки

- Сценарий генерации (успех или тестовый отказ) — локальное состояние ноды: схема графа его не
  хранит, поэтому после перезагрузки он сбрасывается на «Успех».
- Связи создаются только перетаскиванием: способа соединить порты с клавиатуры нет. Поля,
  кнопки и удаление нод с клавиатуры работают.
- Слияния версий при конфликте нет — только «оставить черновик» или «перечитать серверный
  граф», как и допускает задание. Своих правок при перечитывании не сохранить.
- Нода, утащенная за ±10000, после перезагрузки вернётся на границу диапазона.
- Серверный граф не перечитывается в фоне: правка из другой вкладки обнаруживается только
  на следующем сохранении, ответом 412.
- Нет отмены действий, истории, копирования нод, зума картинки в ноде результата и тёмной темы.
- Юнит-тестами покрыты правила и очередь записи, но не React-компоненты: на них смотрят
  сквозные тесты.
- Мобильная раскладка канваса не делалась — по заданию она не оценивается. Служебные экраны
  при этом переносятся.

## Затраченное время

Около 5 часов: примерно час на слой интеграции (`core` + `data`), час на черновик графа и
очередь записи, полтора часа на канвас и ноды, час на устойчивость (конфликт версий,
идемпотентность, восстановление после перезагрузки), остальное — тесты и README.
